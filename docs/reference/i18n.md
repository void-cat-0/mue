`mue-i18n` is an optional localization crate built on the same Fluent resource format as Phira. It depends on `mue-core`, not the renderer or components. It does not modify App/Scene scheduling, initialize fonts, read files, detect system languages, or install a global/TLS translator.

## Resources and namespaces

Enable the `i18n` feature on your `mue` dependency. You can also depend on `mue-i18n` directly if you only need localization.

```toml
[dependencies]
mue = { git = "https://github.com/void-cat-0/mue", branch = "main", features = ["i18n"] }
```

Build an immutable `Catalog` before constructing localized views. Pass Fluent text directly or load bundled files with `include_str!`.

```rust
# #[cfg(feature = "i18n")]
# fn example() -> Result<(), Box<dyn std::error::Error>> {
use mue::i18n::{CatalogBuilder, I18n, langid};

let mut resources = CatalogBuilder::new();
resources.add_ftl(
    langid!("en-US"),
    "library",
    "title = Song library",
)?;
resources.add_ftl(
    langid!("zh-CN"),
    "library",
    "title = 曲库",
)?;
let i18n = I18n::new(resources.build()?, langid!("zh-CN"))?;
let library = i18n.translator("library")?;
# assert_eq!(library.format("title", None).text.as_ref(), "曲库");
# Ok(())
# }
# #[cfg(feature = "i18n")]
# example().unwrap();
```

- English (`en-US`) is the fixed missing-message fallback, **not** the forced initial language.
- Every namespace needs an English resource. Other languages may omit messages or entire namespaces.
- A namespace can contain several FTL resources; different namespaces can use the same message ID. Duplicate message/term IDs within one language and namespace are errors, not implicit overrides.
- `add_ftl` strictly parses and validates one source. Failed sources are not added. `build` creates candidate bundles and only returns a complete Catalog on success; partial bundles are never published.
- Each bundle uses its own resource language for plural rules. Fallback does not merge English entries into a different-language bundle.
- File loading, directory structure and persistent locale settings belong to the application. Resources are immutable in this version; there is no hot-reload API.

## Translation methods

`format` returns one owned snapshot and does not subscribe to locale changes:

```rust,no_run
# #[cfg(feature = "i18n")]
# fn snapshot(library: mue::i18n::Translator) {
use mue::i18n::fluent_args;

let result = library.format("greeting", Some(&fluent_args!["name" => "Ada"]));
let text = result.text;
let language = result.resolved_locale;
let diagnostics = result.issues;
# }
```

Use `text`, `text_with`, or the thin `tl!` macro for retained UI:

```rust,no_run
# #[cfg(feature = "i18n")]
# fn bind_labels(i18n: mue::i18n::I18n, library: mue::i18n::Translator) -> Result<(), mue::i18n::I18nError> {
use mue::{i18n::{langid, tl}, prelude::*};

let view_owner = OwnedScope::new();
let (root, count) = view_owner.run(|| {
    let count = signal(1_u32);
    let root = flexbox()
        .children((
            text(tl!(library, "title")),
            text(tl!(library, "song-count", "count" => count.get())),
        ))
        .into_node();
    (root, count)
});

i18n.set_locale(langid!("en-US"))?;
count.set(2);
// Existing text and layout update; no Node/Scene reconstruction is needed.
# Ok(())
# }
```

`tl!(translator, key)` expands to `translator.text(key)`. Named arguments expand to `text_with(key, move || ...)`.

The translator and key are evaluated once at binding creation; parameter expressions are evaluated once on each formatting evaluation, including when fallback is used. This is syntax sugar, not compile-time key/argument validation.

There is no built-in `ttl!`: use an explicit common-namespace Translator, or define an application alias.

The parameter provider returns owned `FluentArgs<'static>`:

```rust,no_run
# #[cfg(feature = "i18n")]
# fn greeting(library: mue::i18n::Translator, name: mue::prelude::Signal<String>) {
# use mue::{i18n::fluent_args, prelude::Access};
let greeting = library.text_with("greeting", move || {
    fluent_args!["name" => name.get_clone().to_string()]
});
# }
```

Do not return a borrow of a temporary String. Keep numeric values as Fluent numbers rather than turning them into strings, so plural/select rules can inspect their numeric value. `fluent_args!` and `FluentArgs` are re-exported; no parallel argument type system is introduced.

`bind` returns `Prop<Translation>` when diagnostics are needed reactively:

```rust,no_run
# #[cfg(feature = "i18n")]
# fn diagnostics(library: mue::i18n::Translator, count: mue::prelude::Signal<u32>) {
# use mue::{i18n::fluent_args, prelude::*};
let result = library.bind("song-count", move || {
    fluent_args!["count" => count.get()]
});
let caption = result.map(|result| result.text);
# }
```

Create both bindings and projections in the consuming view/node scope.

## Scope, ownership and language selection

`text`, `text_with`, `bind`, and `tl!` **immediately** create reactive resources in the current live, non-null consumer scope. They are not lazy builder expressions.

An expression passed to a builder still runs at configuration time; write it inside a component body or explicit `view_owner.run(...)`. A missing consumer scope is a lifecycle misuse and is rejected, not a translation error.

Parameter providers only read Signal/Prop values and assemble owned arguments. They must not create `map`/`computed`/other reactive resources, mutate the locale, or advance business state.

Parameter-source scopes must outlive the binding. Locale and parameter dependencies remain tracked even when a lookup or argument validation fails, so later corrections update the same binding.

Equal resulting text does not notify text consumers unnecessarily.

`I18n` has the language-changing capability. `Translator` is Clone, fixed to one namespace, and strongly shares the complete service, including its private detached scope and resource Catalog.

Dropping the I18n write handle does not invalidate remaining Translators or their bindings. The final owner releases the service; a copied locale `ReadSignal` alone does not keep it alive.

Consumer bindings are still released with their own scopes, and the service does not hold consumer scopes or callbacks.

Use ordinary `provide(translator.clone())` / `inject::<Translator>()` during view construction if deep components need context. Context follows the scope construction chain, not the Scene stack; callbacks should retain their explicit handle instead of relying on ambient context.

The framework does not provide `install/current`, a service locator, or automatic Scene inheritance.

`I18n::locale()` exposes a read-only Signal and `available_locales()` exposes exact supported identifiers. `set_locale` accepts only an identifier registered in the Catalog; an error preserves the previous language.

There is no implicit `zh-Hant` to `zh-TW` or region-stripping negotiation. A language registered for one namespace can still be selected; missing namespaces use English.

The application may perform system-language negotiation before selecting a supported identifier.

## Keys, fallback and diagnostics

Keys are `message-id` or `message-id.attribute`. Terms (`-brand`) are used inside Fluent resources, not queried as public keys. Invalid identifiers, empty segments and multiple dots return an InvalidKey issue. The namespace is not encoded in the key.

Lookup is:

```text
selected language → en-US → original key
```

Only a missing message, value or attribute advances fallback. Empty formatted text is not a missing value.

Once a pattern is found, references and terms resolve within that complete single-language bundle. Formatting errors preserve its best-effort text and return collected issues; they do not silently switch languages or borrow English terms.

Successful English fallback records `resolved_locale = Some(en-US)`. If no pattern was formatted, `resolved_locale` is None and the original key is displayed.

Resource/configuration errors use `CatalogError` / `I18nError`. Formatting returns owned `Translation { text, resolved_locale, issues }`, with wrapper issues for invalid keys/arguments or missing content and Fluent resolver diagnostics.

Nothing is automatically logged; applications decide how to report issues. An empty issue list is not a guarantee that every Fluent expression was semantically valid.

This first version supports string/number arguments and Fluent selectors, terms, attributes and the internal `NUMBER` function. It does not expose arbitrary custom values/functions, date formatting, a complete regional number/currency formatter or general panic recovery.

Numeric values, precision/options and resource numeric literals are checked before use; unsupported arguments yield diagnostics rather than entering Fluent's unchecked numeric paths. Numbers must be finite with absolute value at most `2^53 - 1`, use at most 18 decimal fraction digits, and keep minimum integer / minimum and maximum significant digit options within `1..=21` (fraction digit options use `0..=18`, with minimum not greater than maximum).

FTL NUMBER inputs are numeric literals, variables or nested NUMBER calls, with literal named options; unsupported static call shapes are rejected during resource registration. Invalid `NUMBER` calls also contribute wrapper diagnostics.

Large integer precision is still bounded by Fluent's f64 representation. A zero minimum-fraction option is normalized to the default to avoid an upstream trailing decimal point on integers; other formatting follows the bounded Fluent behavior.

Fluent BiDi isolation remains enabled; this is independent of automatic RTL layout, which is not added here.

### NUMBER option behavior

`NUMBER` uses Fluent 0.16's bounded rendering, not a complete regional formatter:

- `type: "cardinal"` or `type: "ordinal"` selects the bundle language's plural rules; it does not change the displayed number.
- `minimumFractionDigits` pads the displayed fraction with trailing zeros and changes the visible fraction digit count used by plural selection. For example, `NUMBER(1, minimumFractionDigits: 2)` displays `1.00` and can select a different plural category from `1`. It does not round or truncate existing fractional digits; zero uses the normalization described above.
- `maximumFractionDigits`, `minimumSignificantDigits`, `maximumSignificantDigits`, `minimumIntegerDigits`, `useGrouping`, `style`, `currency`, and `currencyDisplay` do not perform their corresponding precision limiting, integer padding, grouping, percent or currency formatting in this version. In particular, maximum fraction/significant digit options do **not** apply rounding.

Options without corresponding formatting are still retained and validated, and all options participate in upstream `FluentNumber`'s `PartialEq`. A numeric exact variant such as `[1]` therefore need not match the same numeric value with different options; upstream matching is not value-only equality.

## Existing application consumer

The [song-transition application](https://github.com/void-cat-0/mue/blob/main/examples/song-transition/README.md) uses English and Simplified Chinese resources. Its settings Scene switches languages while Library/Details retain their original Node trees, selection and scroll.

The example loads existing bundled CJK fonts; language preference is in-memory only. Locale selection and translation are separate from the renderer's one-time font-system locale initialization.
